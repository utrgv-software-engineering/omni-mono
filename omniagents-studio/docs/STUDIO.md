# OmniAgents Studio

OmniAgents Studio is the local-first experience for inspecting runs, traces, and log artifacts generated by OmniAgents projects. The Studio workstream focuses on unifying tracing, session history, and project-centric workflows into a single UI that runs alongside the core OmniAgents runtime.

## Current Integration Status

- **Package layout**: Studio is its own package, `omniagents-studio/` in the omni-mono repository (Python package `omniagents_studio`), depending on `omniagents`. The FastAPI app is `omniagents_studio/api.py`, the built UI ships in `omniagents_studio/static/`, and the React sources live in `web/`. Trace *recording* is not part of Studio: `omniagents.core.tracing.local` (the `studio` tracing provider) writes the databases Studio reads.
- **CLI entry point**: `omniagents-studio serve` runs the server; `omniagents-studio export` and `omniagents-studio show` cover export and project inspection.
- **Storage unification**: Both OmniAgents session logs and Studio trace archives now live under `~/.omniagents/` (configurable via `OMNIAGENTS_HOME`). Session history is stored at `~/.omniagents/sessions/sessions.db`, while Studio traces and analysis databases are stored under `~/.omniagents/traces/` (one SQLite file per project). The server now creates an empty database when a project is specified, so Studio can launch before any traces exist. This alignment avoids scattering data across ad-hoc locations and prepares the ground for additional Studio features.
- **Manifest discovery**: Run from a project directory (or pass `--project path/to/project.yml`) and Studio loads the manifest for the Playground, Agents and Evaluation views. The trace project is the manifest's `tracing.project`, else its product slug, which a manifest without a `product:` section takes from its directory name.
- **UI branding checkpoint**: The React static bundle now carries OmniAgents Studio naming, with broader navigation and visual updates scheduled for a subsequent iteration.

## Development Workflow

- `omniagents-studio serve --dev` runs the API and Vite dev server together, redirecting the CLI URL to the live-reloading frontend at `http://127.0.0.1:5173`. Otherwise Studio serves a checkout's `web/dist`, or the bundle a wheel ships in `omniagents_studio/static` (built by `make assets`, never committed).
- The web app is an npm workspace of the monorepo and uses the shared packages: `@omniagents/ui` (design system and themes) and `@omniagents/chat-ui` (the chat column the desktop app and the omniagents web UI show).

## Agents and the Playground

Studio does not re-read agent YAML to decide what an agent is. For every
project agent it hosts the real omniagents runtime — the server
`omniagents run` starts, built by `build_app` — at
`/api/agents/<key>/runtime` (`omniagents_studio/agent_runtimes.py`), with the
project directory as its workspace.

- **Agents** (`GET /api/agents/<key>`) shows what a run of the agent is given,
  from `AgentService.describe_agent`: the model after the resolver, the tools
  a run's agent carries (capability tools included) with their approval
  behavior, the instructions rendered for the workspace, subagents,
  capabilities, MCP servers, skills, commands and the approval policy. It is
  read-only: agents are edited in their files, and no endpoint writes them.
- **Playground** embeds the shared chat UI against that runtime: the full GUI
  protocol (approvals, questions, queued messages, attachments, slash
  commands, terminals, reconnect and replay), and conversations land in the
  canonical conversation store like every other client's. The address names
  the agent and the conversation (`?agent=<key>&session=<id>`).

## Logs

Logs reads the project agents' conversations from the canonical
conversation store, through each agent's runtime (`list_threads`,
`search_threads`), so it shows every conversation any client had — the
desktop app, the web UI, the TUI, the Playground and evaluation runs.

- **Review** renders a conversation with the shared chat UI, read-only,
  beside the error-analysis panel (judgment, notes, failure categories).
  Reviews are stored per trace project under the conversation's trace group:
  an evaluation run's own group, otherwise `session_<thread id>`, so reviews
  made on a run's traces stay with its conversation.
- **Evaluation runs** record their scenario, synthetic selection and expected
  outcome on their conversation (thread metadata `omniagents`, the same block
  their trace carries). Logs filters by run kind and by those dimensions, and
  an evaluation result's "Open conversation" link lands on the run.
- **Timing** shows the traces a conversation's runs recorded, when tracing was
  on; it is the only part of Logs that reads traces.

## Lifecycle Coverage

- Priority focus: all lifecycle steps below are high priority for Studio parity unless flagged otherwise. Optimization flows remain lower priority follow-ups.

- Create an AI agent
  - CLI: `omniagents new` or `omniagents generate agent` scaffolds projects and agent YAML.
  - Studio: Agents are created and edited in their files; Studio shows what the runtime resolves.
- Configure dimensions
  - CLI: Update `evaluations/evaluation.yml` directly or run `omniagents generate eval quickstart` for starter content.
  - Studio: Dimensions tab offers full CRUD persisted back to `evaluation.yml`.
- Generate scenario sets
  - CLI: `omniagents eval scenarios generate` invokes the async generator with count, seed, filters, and output options.
  - Studio: Scenarios tab starts generation jobs with progress/output wiring and can delete generated or annotated sets directly.
- Run scenario sets and capture traces
  - CLI: `omniagents eval scenarios run` executes YAML sets and records runs plus Studio traces.
  - Studio: Scenarios tab launches run jobs, tracks status, links artifacts, and surfaces a “View Run” shortcut into Logs.
- Review traces and apply judgments
  - CLI: Requires launching Studio via `omniagents-studio serve`; no inline review tools.
  - Studio: Logs workspace supports binary judgments, notes, failure category tagging, and can be opened directly via “View Run” buttons on scenario runs and datasets.
- Annotate scenario sets with failure categories
  - CLI: `omniagents eval scenarios annotate` enriches scenario YAMLs with failure_categories using Studio judgments.
  - Studio: Scenarios tab offers an “Annotate Failures” action that emits `annotated_scenarios.yml` alongside the set.
- Split datasets into train/dev/test
  - CLI: `eval scenarios split` wiring is incomplete despite available helpers.
  - Studio: No splitting controls; datasets panel is read-only.
- Create an LLM judge
  - CLI: `omniagents generate judge` scaffolds judge manifests tied to failure categories.
  - Studio: No judge authoring experience.
- Optimize the LLM judge
  - CLI: `omniagents judge optimize` runs GEPA loops over splits.
  - Studio: Optimization flows are absent (lower priority).
- Add golden scenarios
  - CLI: Manually edit `evaluations/scenarios.yml` or craft scripts.
  - Studio: Scenarios tab promotes generated or annotated entries into the golden set.
- Run the evaluation suite
  - CLI: `omniagents eval suite run` compiles and executes scenarios with TAP or JSON output.
  - Studio: Suite execution and reporting have not been surfaced.
- Optimize the agent
  - CLI: `omniagents agent optimize` iterates on instructions with optional apply.
  - Studio: No agent optimization tooling (lower priority).
- Confirm golden scenarios pass
  - CLI: Rerun the suite and inspect results manually.
  - Studio: No automated gating or dashboards around golden pass rates.

## Motivation

1. **Single release train** – Shipping tracing and log tooling in the same repository keeps Studio improvements aligned with OmniAgents releases. There’s no longer a lag between core runtime changes and tooling updates.
2. **Shared filesystem layout** – Locating sessions and trace databases in `~/.omniagents/` simplifies support, backup, and eventual cloud sync stories. Both the OmniAgents runtime and Studio now read consistent paths.
3. **Studio as the primary UI** – Consolidating tracing into `omniagents` lays the foundation for a broader “Studio” concept: an opinionated interface that can inspect instructions, logs, traces, and synthetic data. Early integration reduces future churn when the UI grows beyond tracing.
4. **Strict migration** – Because the project has not reached production, we opted for a strict cut-over instead of maintaining compatibility layers. The CLI commands, directories, and data paths all reflect the planned Studio nomenclature without shims.

## Next Steps

- **Manifest-aware runtime**: Teach `omniagents-studio serve` to inspect the current working tree for `project.yml`, infer the entry agent, and preload project metadata so the UI can display context immediately.
- **UI updates**: Rebrand the React bundle to “OmniAgents Studio” and tighten navigation around core workflows (run review, logs, synthetic data). This will incorporate OmniAgents conventions (agent names, workflow keys, failure categories) directly into the interface.
- **Studio Python utilities**: Expose higher-level helpers under `omniagents_studio` for scripts and notebooks (e.g., opening Studio, exporting annotations, inspecting traces).
- **Documentation**: Expand this document with quickstarts, command references, and troubleshooting guidance once the auto-discovery and UI work land.
- **Beyond tracing**: Evolve Studio into the control plane for OmniAgents projects—think dbt Cloud for agents—covering manifest management, log orchestration, artifact review, and collaborative annotations. Tracing remains the baseline feature, but every change should keep the broader “project cockpit” vision in mind.
- **UI parity with CLI**: Gradually surface major `omniagents` CLI flows—agent creation, guardrails, scenario generation, log suites, agent-as-judge scaffolds, optimization runs, and project compilation—directly in the Studio so users can launch workflows without leaving the UI.
- **Playground and experimentation**: Provide a scratchpad for rapid agent iterations, lightweight prompts, and tool call experiments, wiring results back into trace storage so experiments stay auditable.
- **Judge lifecycle**: Add first-class screens for creating, testing, and optimizing Agent-as-Judges, aligned with the CLI’s `agent optimize` and log utilities.

Studio is now part of the OmniAgents repo, wired into the CLI, and ready for deeper integration with project manifests and log tooling. Further iterations will flesh out the experience into a full control center for building and refining OmniAgents projects.
