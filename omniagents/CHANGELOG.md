# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- `omniagents.core.eval.workspace.EvalWorkspace`: a project's evaluation as one object, used by the CLI and Studio. It edits dimensions, failure categories (removing one takes it off every scenario), measure descriptions and stubs, scenario sets (project files and generated sets: add, update, remove, promote, label with a review), judges (inline or `judges/<key>/`), judge datasets and the holdout, all in place so comments survive; and it runs the suite or a scenario set, saving each run with its manifest and conversations, and lists, reads and compares saved runs. `results.compare_runs` reports every manifest difference and compares pass rates only when the runs used the same scenarios the same number of times.
- `omniagents eval scenarios run --set <generated_scenarios.yml>` runs every scenario of a scenario set, saved beside it.
- `omniagents judge dataset --set <name> -c <category>` builds a judge's train/dev/test dataset from a reviewed generated set.
- `omniagents.core.project.agent_files`: one way to edit a project agent. `read_agent`, `update_agent(changes=..., instructions=...)`, `write_agent_yaml`, `create_agent` and `delete_agent` edit `agent.yml` as a round-trip document, so comments, key order, quoting and indentation outside the edited settings are kept (`omniagents.core.utils.yaml_edit`; `ruamel.yaml` is now a dependency). A candidate is loaded exactly as a run loads it before it is written, and is refused (`AgentEditError.problems`) if it introduces a problem: an unknown tool, capability, guardrail or agent, a wrong `name`, or instructions that are not a valid template. Instructions are saved where they live, inline or in the `instructions_file`.
- `AgentService.describe_agent` reports `guardrails` (`input`, `output`, `tool_input`, `tool_output`) and `output` (the structured output's name, strictness and JSON schema, or `null` for text).
- The transcript records what a prompt was sent with: a 256px thumbnail per attached image and the name of each attached file, under the user message's `content.attachments` (`[{type, url?, filename?, mime?}]`) and on `run_started`. Clients show them on the message (Ink as `[image]`/`[file: name]` markers); before, a sent image vanished from the chat. `pillow` is now a direct dependency.
- Ink theming with Omarchy palettes. The TUI's colors are now a theme: an Omarchy `colors.toml` palette resolved with Omarchy's own alias and shade cascade (`tui/src/theme/palette.ts`, checked against `omarchy-theme-color`) and mapped onto the design system's semantic roles (`theme/roles.ts`); `Theme.*` reads stay as they were and resolve live. All 22 Omarchy themes are bundled (`theme/bundled.ts`, vendored by `tui/scripts/import-omarchy-themes.mjs`, MIT). `/theme` opens a picker with a swatch preview; Enter applies and saves to `<product config>/ink.json`. On an Omarchy desktop the TUI follows the desktop's current theme by default and retints live on `omarchy-theme-set`. User themes load from `<product config>/themes/`. Precedence: `--theme`, saved choice, `OMNI_THEME`, Omarchy, `tokyo-night`. The ink backend passes `--themes-dir` and `--settings-file` to the TUI.
- Evaluation runs are now comparable, repeatable and sliceable. Every run record carries `trial` (which repeat of the scenario it is, 0-based; `runs_per_prompt` fans out but used to flatten repeats indistinguishably) and `answered` (whether the agent produced a final answer at all - a different failure from a wrong one, and previously counted as one). Every `pass_rate` metric carries a 95% Wilson `interval`; a metric or `evaluation.defaults.slice_by` may name scenario fields (`expect.skin_tone`, `tags`) and the rate is then also reported per value under `slices`; `exclude_nonresponse: true` drops unanswered runs from a metric's denominator, and the new `answered_rate` metric type reports them. Results metadata gains a run **manifest** (model, resolved tools, instruction and agent-file hashes, framework version, selector, split, repeats - `omniagents.core.eval.manifest.build_run_manifest`) so two runs can be compared, or refused. New `omniagents eval scenarios holdout --strata <field,...> --fractions 0.5,0.25,0.25 --seed <n>` writes a seeded, stratified train/dev/test assignment (names only) under `evaluations/splits/eval/` with a manifest, and `eval suite run --split test` selects it - distinct from `eval scenarios split`, which partitions by failure-category label to train a judge. Notebook: `EvalSuite.run(agent, repeats=N)`, `EvalResult.trial` / `.metadata` / `.answered`, `EvalSuite.add(metadata=...)`, `from_records(metadata_fn=...)`, and on `EvalSuiteResults`: `pass_rate_interval`, `answered_rate`, `by_case()`, `by_field("skin_tone")`.
- Client tools now reach realtime voice sessions. A voice session started with a GUI session id (the web UI already passes it) bridges that GUI session's `variables.client_tools` into the `RealtimeAgent`'s tool list; invocations broadcast `client_request {tool.call}` over the GUI session's channels exactly as in text runs, so a GUI client's tool handlers serve voice with no changes. Because the realtime pipeline has no tool-approval flow, only tools registered with `safe: true` are bridged — approval-gated tools stay text-run only rather than silently losing their gate — and ownership is checked (`AuthorizationPolicy.can_access`) before bridging, so a realtime principal cannot borrow another user's client tools. New surface: `AgentService.build_realtime_client_tools(session_id, principal=None)`, `RealtimeSession(extra_tools=...)`, `RealtimeService(agent_service=...)` (wired in `build_app`). No wire-protocol change on `/ws/realtime`.

### Changed (BREAKING)
- A saved run is complete. `results/<run_id>/results.json` holds everything the engine returned (runs with their conversations, `summary` with its interval, `stats`, `metrics` with slices, `warnings`, `manifest`); it used to keep only `runs`. `results/runs.json` entries carry the pass rate, its interval and the manifest. `save_evaluation_run(scenario_path, data, *, source, scenario_name, agent, workflow_name)` takes the manifest from `data`; `save_run_results` and `update_runs_index` are private to it. Run ids gain a random suffix so two runs in one second do not collide. `results.read_run`, `list_runs`, `compare_runs` and `conversations_for` read runs back.
- `omniagents eval suite run` saves into the evaluations directory's `results/` (beside the scenarios it ran) instead of `artifacts/eval/<name>/results/`; `--name` labels the run. `-o/--output` (or `evaluation.output`) now writes a copy of the saved `results.json` in addition to it.
- Judges read the conversations of the scenario set's newest saved runs. `generated_runs.json`, which nothing wrote any more (so `judge run` and `judge optimize` could not run), is gone; `--runs-file` takes a saved `results.json`. `OmniAgentsJudgeAdapter` takes those conversations (scenario id -> run) instead of a file path. `judge optimize` starts from the judge's own instructions and template; it read them from `agent.yml`'s former `evaluation:` block and started from a generic prompt.
- `eval scenarios split` is removed (it never had a handler and printed a usage error); use `omniagents judge dataset`.
- A judge's `instructions_file` and `template_file` resolve against the YAML that declares the judge (`judges/<key>/judge.yml` or `evaluation.yml`), and a missing file is an error when the evaluation loads; a run used to fall back to generic judge instructions silently. The judge template writes `instructions.md`/`template.md` (it wrote a `../evaluations/judges/<key>/` prefix that only resolved from the evaluations directory), and `scaffold_judge` writes into the configured evaluations directory (`paths.evaluations`). Judges declared inline in `evaluation.yml` and in `judges/` are merged; the `judges/` ones used to replace them all.
- `pipeline._load_local_measures` is `load_project_measures`: it returns the measures it loaded, replaces what an earlier load registered (an edited `measures.py` takes effect in a long-running process; two projects never share a measure by name), and raises when a `measures.py` cannot be imported instead of silently running without it.
- `pipeline.run_evaluation` accepts `eval_cfg` and `include_history` and returns the traces' `workflow_name`.
- Agent configuration problems are logged, not printed. The loader's 124 `print("Warning: ...")` calls go to the `omniagents.core.config.loader` logger (stderr by default) and can be collected with `collect_config_problems()`. Removed: `omniagents.core.project.apply.apply_agent_instructions` (use `agent_files.update_agent(..., instructions=...)`; its fallback to the current directory's `project.yml` is gone) and `omniagents.core.project.scaffold.delete_agent` (use `agent_files.delete_agent`, which keeps `project.yml`'s comments).
- A host `git-remote` source must carry `checkoutPath`, the directory its clone lives in; the provisioner no longer clones into each Workspace's materialization root. The caller picks one path per project source, so every Workspace of a project shares one checkout, the way local folders are shared (the desktop had made a 300 MB clone per chat). First clones are serialized with a lock beside the checkout; `filelock` is now a direct dependency.
- Tracing is off by default. `ProjectContext.tracing_defaults` is now `{provider: none, project: <slug>, name: <slug>}` and `setup_tracing(None)` disables tracing; set `tracing: {provider: studio}` in `project.yml` to record locally. An always-on recorder grew `~/.omniagents/traces` without bound (8 GB on one desktop). Evaluations still record locally unless the manifest declares a provider, since Studio's review screens read them. The `default` provider alias is gone.
- **OmniAgents Studio is no longer part of omniagents.** The server, UI and CLI moved to the `omniagents-studio` package in the omni-mono repository; launch it with `omniagents-studio serve` (also `export`, `show`). Removed from omniagents: the `omniagents studio` command, `omniagents.studio`, the `omniagents.agentio` alias, and the `studio` / `studio-server` extras (`[all]` no longer includes them). Trace recording stays in omniagents as `omniagents.core.tracing.local` (`init`, `trace`, conversation-analysis helpers; `LocalTraceProcessor` was `StudioTraceProcessor`), so `tracing: {provider: studio}`, still the default, records to `~/.omniagents/traces/<project>.db` without Studio installed. The remote trace processor (`init(server_url=...)`) is gone: it posted to a `/api/trace` endpoint the Studio server never had.
- **One evaluation engine.** `omniagents eval suite run` / `eval scenarios run`, Studio jobs and the notebook API now run scenarios through one implementation, `omniagents.core.eval.engine` (`run_scenario`, `run_suite`); only the agent differs, through an `AgentTarget` (`core/eval/targets.py`: `ProjectAgentTarget` builds the project agent from `agent.yml`, `SdkAgentTarget` drives an `agents.Agent` with the SDK `Runner`). The CLI's two runners (`pipeline._run_scenario` for plain prompts, `multi_turn.*` for environments, `prompts` and synthetic scenarios) are merged into it and `core/eval/multi_turn.py` is deleted; `run_scenarios_against_agent` moved to the engine, `pipeline._run_judges(cfg_path, ...)` is `pipeline.run_judges(eval_cfg, scenario, history, base_dir)` (one judge: `run_judge`), and `build_run_manifest` takes the agent description (`describe_agent_config` / `describe_sdk_agent`) instead of an `EvalConfig`. Every run record now has the same fields whatever the scenario type: `passed`, `answered`, `trial`/`repeats`, `trace_group_id`, `type`, `exchanges`, telemetry, and `metadata.environment_context`; every result has `summary` (whole-run pass rate with its Wilson interval), the full `stats` and the `manifest`, whose `select`/`exclude`/`split` come from the loaded config (`EvalConfig.select`/`.exclude`) and whose `max_turns` is the limit the run used (`defaults.max_turns` when set). A run counts as passed when every measure on it passed (`core.eval.metrics.run_passed`, used by results storage, Studio and the notebook alike); a run that could not execute carries a failing `_run_error` measure instead of passing with no measures.
- **The notebook API is a layer over the engine.** `EvalSuite.run` turns its cases into scenario dicts (`EvalSuite.to_config()` shows the evaluation config it runs, in the shape of `evaluation.yml`) and wraps the engine's run records (`EvalResult.record`); `EvalSuiteResults` carries the engine's `metrics`, `stats` and `manifest`, and its rates and `by_field()` slices use the engine's helpers, so a suite produces the same outcomes, metrics, intervals and manifest as the CLI. New: `EvalSuite.from_project(path, select=, exclude=, split=, agent=)` loads a project's `evaluations/` folder through the CLI's loader; `await suite.run()` then runs the project agent exactly as `eval suite run` does, and `suite.run(agent)` an agent built in code against the same scenarios. `run(agent)` accepts an `agents.Agent`, an `agent.yml` path or an `AgentTarget`. What the notebook implemented itself now comes from the engine, which changes some behaviour: runs execute concurrently (`concurrency=5`, as the CLI); `repeats` and `max_turns` default to the config (`defaults.runs_per_prompt` / `defaults.max_turns`; an `agents.Agent` still gets 10 turns), and a scenario's own `runs_per_prompt` wins; `expect` checks (`tool_called`, `response_contains`, `verify`, ...) are the builtin `expectations` measure (`core/evaluation/expectations.py`) that `add()` attaches when those keys are used, and `verify` without a real environment fails; a synthetic case's "goal reached" rule is the builtin `user_goal_achieved` measure, and synthetic cases use the engine's simulated user (`SyntheticUser` is now that class with a goal-first constructor); `max_exchanges` applies to synthetic cases only (scripted `prompts` all run); `Judge` is an `evaluation.judges` entry (`Judge.to_config()`) scored by the `<name>_agent` measure it registers, answering `{"answer": "Pass"|"Fail", "reasoning", "score"}`; a judge named by string that is not a notebook `Judge` is a config judge listed under the scenario's `judges`; an environment teardown failure is logged, not a failed run; `include_builtin_measures` and `include_unmeasured` default to on for a hand-built suite and off for `from_project` (the CLI's defaults). Measures may be `async def`; the engine runs them with the new `run_measures_async` (sync `run_measures` refuses them).
- Dropped fallbacks for library versions outside the pinned ranges: websockets' `extra_headers`, pre-3.10 `importlib.metadata.entry_points()`, and the agents SDK's argument-less `MCPServer.list_tools` retry.
- **Serve protocol 3.** `<prog> serve` takes `--exit-on-stdin-close`: serve shuts down when stdin reaches EOF, so a launcher that spawns it with a never-written stdin pipe takes serve down with it even after a crash. The spawn argv changed, so `SERVE_PROTOCOL_VERSION` (and `describe --json`'s `serve_protocol`) is now 3; launchers that require 3 refuse an older runtime instead of failing on an unknown flag. `--credential` and `--snapshot-dir` are documented as container-only.
- The MCP and Codex store-durability attestation is gone: `OMNIAGENTS_MCP_STORE_DURABILITY` / `OMNIAGENTS_CODEX_STORE_DURABILITY` are no longer read, `account_status` returns `{providers, selected_provider}` without `mutation_persistence`, and `mcp_list_servers` reports managed server names as a top-level `managed_servers` field.
- **Slash commands are declared, not inferred from the server function registry.** A server function is an RPC; it becomes something a person can type only when it carries a slash declaration: `@slash_command(name, description=..., usage=..., args=none()|text(field)|words(...), during_run=..., order=...)` next to `@server_function`, or a manifest `slash_commands:` binding (which `AgentService` now registers as a server function of the same name carrying the declaration, and which gains `description` and `usage` keys). The catalog is `server_call("slash.list")`; clients render only that in popups and `/help`, map the typed line through the declared argument rule (never JSON), and refuse an unknown `/name` with "Unrecognized command" instead of sending it to the model. Slash names are single words with no dots, Codex-style: a verb with several actions takes its mode as the second word (`/goal`, `/goal <text>`, `/goal stop|pause|resume`; `/loop`, `/loop [interval] <prompt>`, `/loop stop [id]|clear`) or opens its panel (`/goal`, `/loop`, `/jobs`, `/artifacts` in Ink, which gained goal and loop drawers alongside jobs and artifacts, with the verb's actions as keys). Builtins declared typeable: `help`, `model`, `models`, `reasoning`, `compact`, `recap`, `goal`, `loop`, `good`, `bad`, `jobs`. The `artifact` display function is host-facing and is not typeable. Ink adds the session verbs Codex has and we lacked: `/new`, `/rename <title>`, `/fork`, `/diff` (alias `/review`), `/status`, `/mcp`, `/skills` (a drawer: type to filter, Enter reads the SKILL.md in place, backed by new `skills.list` and `skills.read` RPCs in the `skills` pack), `/copy` (OSC 52), `/export` (markdown to the working directory), and `/pwd`; every drawer and screen opens from a verb (`/tasks`, `/queue`, `/notifications`, `/git`, `/workers`, `/terminal`) and the ctrl+a panel menu is gone. The dotted `goal.*`, `loop.*`, `bash_jobs.*` and `bj-*` functions remain as RPCs the panels call. Everything else (`session.*`, `mcp.*`, `terminal.*`, `sandbox.*`, `bash_jobs.*`, `cron.*`, `fs_*`, `git_*`) stays an RPC and disappears from the user's view. `list_server_functions` is unchanged.

  Removed with it: the model-side `dispatch` tool, the `slash` capability pack, `omniagents.core.tools.SlashCommandRegistry` / `register_slash_command` / `default_slash_registry`, and `slash_agents.manifest_slash_handler`. Products that listed `slash` in `capabilities:` or `dispatch` in `safe_tool_names` drop both; their manifest `slash_commands:` keep working and now show up in every client's `/` popup.

### Changed (BREAKING)
- Tracing is off by default. `ProjectContext.tracing_defaults` is now `{provider: none, project: <slug>, name: <slug>}` and `setup_tracing(None)` disables tracing; set `tracing: {provider: studio}` in `project.yml` to record locally. An always-on recorder grew `~/.omniagents/traces` without bound (8 GB on one desktop). Evaluations still record locally unless the manifest declares a provider, since Studio's review screens read them. The `default` provider alias is gone.
- **Run ownership is a heartbeat lease, and `/recover` is gone.** A run's reservation now carries a heartbeat the owning process refreshes every 5 s; a reservation whose heartbeat is older than 30 s belongs to a runtime that died, and the next `start_run` takes the session over on its own: the interrupted turn is closed as failed, any tool call that never reported lands as "outcome unknown" (the same note the model already received through history repair), and queue items the dead dispatcher had claimed go back to pending. The previous design retired a reservation only on Linux process-identity proof (machine id, boot id, PID namespace, PID start time) plus executor cleanup journals, and otherwise waited for an operator to run `/recover`, or `/recover {"abandon_unknown_run": true}` for reservations written before 0.7.36, which could never be proven dead. That ritual is deleted along with `omniagents.core.runtime.ownership_recovery`. Queue items no longer have a `dispatch_uncertain` state: a claim is a short lease too, `cancel_queued_message` always removes the item, and a dispatch whose `start_run` raised is marked `failed` with the reason instead of pausing everything behind it. The "Waiting for the previous runtime" annotation is gone with it. Executor journals and descendant reaping are unchanged; they still stop processes, they just no longer gate the lease.

### Fixed
- `omniagents eval suite run` no longer looks up scenario line numbers in `agent.yml` (a leftover from when scenarios lived there; it never found any).
- `agent optimize --apply` no longer hides a failure to apply: the result carries `applied` and `apply_error`, and the run log says why. Applying goes through `update_agent`, so inline instructions keep the rest of `agent.yml` as it was.
- The empty conversations that reads left behind are removed. Before reads stopped creating threads, every chat a client merely opened was kept as an empty conversation and listed beside the real ones. The first open of a SQLite conversation store after upgrading deletes, once, each thread nobody made anything in (no items, turns, title, metadata, branch parent, pin, usage or submission, and nothing queued) that was not touched in the last five minutes, and records that in `PRAGMA user_version`. Worker reference threads are kept. Postgres stores are not cleaned.
- Clients introduce themselves truthfully in `initialize`. The shared client sent `omni-desktop` 1.0.0 on a `browser` platform from every app; the web UI now sends `omniagents-web`, the TUI `omniagents-tui` (both at the omniagents version) with its real OS and architecture, and Studio `omniagents-studio`. The TUI's `--version` printed nothing and now prints the omniagents version.
- Builtin capability instructions no longer name tools from other packs. `filesystem` and `filesystem_readonly` told the model to search with `execute_bash`, `markdown` pointed at `download_file`, `serpapi` at `web_fetch`, and `wakeup` at `execute_bash` and `spawn_worker`; an agent without those packs was told to call tools it did not have. The `rg` search guidance stays in `shell` and `shell_readonly`, which supply `execute_bash`. A test now fails if any builtin pack mentions another pack's tool.
- After Stop, a new message is accepted as soon as `run_end` arrives. Stopping a run while its command tree was still being retired deferred the session release to that cleanup, but `run_end` went out at once, so a message sent on it was refused with "Session has an active runtime owner". `run_end` now waits (up to 30 s) for the release.
- Replies and tool calls from providers without Responses ids (chat completions, most OpenAI-compatible endpoints) are each kept once. Every such reply carries the agents SDK's placeholder id `__fake_id__`, which the transcript took as a real id, so only a chat's first reply was recorded; and a tool call without an `id` was saved twice, so the next request repeated it. The placeholder is never stored or used as an identity (`conversation.model.provider_item_id`), tool calls are matched on `call_id`, and the end-of-run flush matches id-less messages on role and text against the run's own rows.
- `Runner.run_notebook` shows the agent it started, every time. It probed ports 8080-8099 by binding and closing a socket, then started uvicorn on the number in a background thread and waited until something accepted a connection on it. Two kernels starting at once picked the same port: the loser's uvicorn failed to bind (silently, in its thread) while the readiness probe reached the winner, so the notebook displayed the other kernel's agent. Ports in TIME_WAIT from a just-restarted kernel counted as taken, and every re-run left its server running on the next port, so after twenty runs (or right after a restart) it raised "Could not find available port". The server now listens on a socket bound up front (port 0 unless `port=` is given; a taken explicit port raises `OSError` instead of showing whatever holds it), readiness is uvicorn's own startup signal, and re-running replaces the runner's previous server (`Runner.stop_notebook()` stops it). The Ink backend (`ws://` URL handed to the TUI) and the web backend (still 8080 first, now held from bind to serve) start their servers the same way, through `omniagents.core.utils.serving`.
- `<prog> serve` prints its readiness payload once it is accepting connections. It printed the payload before uvicorn had bound the port, so a launcher dialing on reading it was refused; it also chose the port by binding and closing a probe socket first. Serve now binds its own socket (port 0 by default) before building the app, and a taken `--port` fails before anything starts.
- Evaluations with an environment, scripted `prompts` or synthetic scenarios (all of omni-code's) ran on a second runner that recorded no `trial`, `answered`, `trace_group_id`, run manifest, `slice_by` default slices, failure-category measures, unknown-measure warnings or scenario counts, and never ran judges for synthetic scenarios; they now run on the one engine and record everything a plain prompt does.
- Evaluation telemetry recorded zero token usage for every project agent: a project agent's stream carries usage as `token_usage` items, which the eval did not read.
- Scenarios written inline in `evaluations/evaluation.yml` ignored `--select`, `--exclude` and `--split`.
- A message sent into a chat whose context needs compacting reaches the model. Compaction that ran before a turn's first model call rebuilt the request from saved context, which does not hold the new message yet, so the model answered the previous turn again. The rebuilt request now keeps the unsaved tail (native and checkpoint compaction alike).
- Inline images no longer look like millions of tokens to the compaction trigger: an image costs its pixel area (32px patches, read from the PNG/GIF/JPEG header), not its base64 length. A large uploaded photo had made every turn compact, and compaction keeps user messages, so it never got smaller. The checkpoint summarizer's transcript replaces inline image and file payloads with placeholders.
- `/compact` returns `{ok, message}`. It returned a bare string, which the `server_call` result schema rejects, so every typed `/compact` reported an error even when compaction succeeded.
- A server started with a default environment (the TUI, the web UI, the notebook) binds every new thread to it, the same thread binding the desktop controller makes with `agent_host_bind_thread`, and every operation routes through the thread's binding alone: a `server_call`, `start_run` with `inherit`, a realtime or pipeline voice turn. The separate default-environment fallbacks in `AgentService`, `RealtimeService`, `VoicePipelineService` and `prepare_environment_context_for_session` are gone, so a code path can no longer forget one. `/jobs` and similar commands failed as the first thing typed in a TUI session for that reason. The TUI and web UI start runs with `{"mode": "inherit"}` instead of copying the handshake's `default_environment_id` into each `start_run`; the handshake still advertises it for the file and git panels.
- Manifest slash agents (`/init`) are routed to the session's environment and bind its workspace for the agent's tools; they ran with no workspace ("No workspace is bound to this run") and anchored to the server's `$PWD`. A failed run's message now carries the error.
- `server_call` picks a function's calling convention from its signature and calls it once; a `TypeError` raised inside a function was taken as a signature mismatch and the function re-run with other arguments.
- Closing a terminal ends what is running in it. The host backend hangs up the shell (SIGHUP, as closing a terminal window does) instead of sending SIGTERM, which an interactive shell ignores, before the SIGKILL that kept it from hanging up its jobs; and it no longer waits on a live shell when its output reader is cancelled, which had kept `close()` from ever running. The session backend still sends its Ctrl-C/Ctrl-D when the reader's cancellation has already marked the handle closed.
- Notebook runners now register a host execution environment rooted at the current working directory, with a `default_host_workspace_root` override. Filesystem tools such as `read_image` and `read_file` work again without relying on an implicit workspace fallback.
- Slash command output is command output, not the agent's words. Ink renders a typed verb's result as its own `command` transcript row (headed by the verb, in chrome), so `/status` no longer wears the agent's color and `/copy` never copies it; `/export` writes it as a fenced block. Results are normalized in one shared helper across Ink, web, and the launcher: a string is the message, `message` or `text` is the message, anything else prints "Done." instead of a JSON dump. That fixes `/recap` (was a raw `{ok, text}` object) and `/compact` (was a quoted string); `/recap` now also returns `message`.
- Ink mode no longer leaks the terminal to tool commands. After handing the screen to the TUI, the Python server moves its own fd 0/1/2 off the tty (`detach_terminal` in the ink backend), and `HostWorkspace.exec` runs every one-shot command with `stdin=DEVNULL`. Before, a tool command inherited the terminal Ink reads in raw mode: one that read stdin stole keystrokes, and one that found a tty there reset it to cooked mode on exit, leaving the TUI echoing typed keys and mouse reports as text.
- Ink footer drawers (Skills, Bash jobs, Artifacts, Tasks, Queue, Notifications, Git, the command palette) render one terminal line per row and size their document panes to at most half the terminal. Long names, descriptions, commands, subjects, and log lines used to wrap, so an eight-row list could take twenty-five rows and push the drawer's hint and border off the bottom. The rules live in `shared/drawer-layout.tsx` (`Fixed`, `Clip`, `oneLine`, `useDrawerBudget`).
- Voice sessions can spawn workers again, and lease-routed tools work in voice at all. A realtime session's tool calls execute in the SDK's model-listener task — outside any Run — so `RealtimeSession.connect()` bound only the workspace contextvars and left the two bindings `start_run` makes unset: the routed `RequestContext` and `_current_service`. Everything downstream degraded silently. `spawn_worker` reached `worker_tools._host_resources()` → `current_service()` → `None`, so the worker's `LocalAgent` composed a **private** `AgentHostResources` bundle; its run then selected the parent's environment explicitly and failed with `EnvironmentNotFoundError: execution environment '…' was not found`. With no request context, `serve_worker_sources()` returned `[]` (worktree isolation had no sources), `default_worker_project_context()` fell through to the installed product manifest instead of the live AgentDefinition, and `require_environment_lease()` rejected `skill_tool` / `sandbox_observe`. Worker completions were dropped too — `_on_worker_complete` and `emit_subagent_event` both no-op without a current service — so even a worker that did start never woke the session or appeared in the panel. `connect()` now binds both, before `__aenter__` so the listener task inherits them and deliberately without reset so the event-pump task (where an approval-gated tool resumes, via `approve_tool_call`) inherits them too. New public surface: `AgentService.bind_current_service` / `reset_current_service`; `AgentService.acquire_environment_for_session` became `prepare_environment_context_for_session` and returns the whole routed context (the caller binds it) instead of only its lease, and `RealtimeSession(environment_lease=...)` became `RealtimeSession(request_context=...)`, deriving the lease from it.
- `realtime_history_updated` / `realtime_history_added` now carry each item's `item_id`. They read a bare `id`, which only `RealtimeResponse` has — `RealtimeItem` (message or tool call) names it `item_id` — so every entry in the ordering snapshot was `null` and the event was useless to clients. It is the only thing that tells a client the model's real conversation order, which matters because input transcription is asynchronous: a user turn is transcribed after the reply it prompted, so a client appending on arrival renders the answer above the question. Documented in `realtime_protocol.md`.
- A session-scoped `server_call` may create the session it names. `authorize_rpc` resolved a not-yet-existing session to "unowned", and unowned is never consent, so the call that *creates* a session was refused: `-32014 Not authorized to access this session`. Resident agents could not start at all — their day session (`resident-<id>-<date>`) is a new id every day and `server_call {session.ensure}` is what brings it into existence. Text chat never hit it because `start_run` binds a routed request context, so authorization checks the workspace owner instead of the session. The exemption is an allowlist of one (`SESSION_CREATING_SERVER_FUNCTIONS = {"session.ensure"}`) and applies only when the session genuinely does not exist: every other session-naming method still fails closed on an unknown id — `resume_session` above all, whose `get_or_create` would re-materialize a deleted session's journal on every reconnect — and a session that exists *with* no owner stays denied, since that is the legacy row `python -m omniagents.core.session.backfill --user-id <principal>` is for.
- A realtime session that resolves to no environment logs a warning instead of failing silently much later inside a tool.

### Security
- Unified authentication across every WebSocket surface: `/ws`, `/ws/realtime`, and `/ws/terminal` now resolve one authenticated principal through the configured `AuthProvider` (`omniagents.rpc.auth.ConnectionAuthenticator`). Credentials travel as `Authorization: Bearer` headers (native clients) or one-time `POST /auth/ws-ticket` connect tickets (browsers); the query-string `?token=` transport is deprecated and disabled by default — re-enable during migration with `OMNIAGENTS_LEGACY_QUERY_AUTH=1` or `security.legacy_query_auth: true` (a deprecation warning, never containing the token, is logged on use). Terminal attach credentials moved from the URL to a first-message `{"type": "attach", ...}` frame, and the serve readiness payload gained a dedicated `auth_token` field (`ws_url` carries a token suffix only under the legacy flag).
- Authorization fails closed everywhere: an ownership lookup that cannot answer denies (never reads as "unowned"), a request naming no resource must be explicitly classified as globally safe (process-wide mutators `disable_tool` / `disable_mcp_server` are refused in multi-user mode), unowned legacy sessions are inaccessible instead of being silently claimed by the first caller (explicit migration: `python -m omniagents.core.session.backfill --user-id <principal>`), and self-scoped listings filter in SQL so ownership composes with pagination. Deployments that identify no principals (the `NoneAuthProvider` default) short-circuit all of it, so single-user behavior is unchanged.
- Session/run/terminal/approval ownership is enforced centrally: sessions persist the creating principal's `user_id`, `JsonRpcEndpoint` authorizes every request through the service's `authorize_rpc` before dispatch (so new methods inherit enforcement), terminals and realtime sessions bind to their creator, and `list_sessions` / `get_user_history` are scoped per user. Cross-user access is rejected with the typed JSON-RPC error `-32014` (`authorization_denied`, specified in `omniagents/rpc/protocol.md`; the frozen v1.0.0 OpenRPC document is left untouched, so the error joins the generated contract with the next protocol version); connection-level auth failures close with terminal codes 4401/4403 that clients (web, Ink) treat as non-retryable, so bad credentials never enter reconnect loops. `TokenAuthProvider` gained a multi-token `tokens:` map for multi-user token deployments.
- Per-user identity now survives the serve proxy hop (`remote_agent.ws_url`). Previously the proxy authenticated the local user and then presented **every** proxied connection the same shared `auth_token_env` credential upstream, so the upstream saw one principal and the ownership model above could not separate proxied users — bob could read alice's transcript through a proxy. The proxy now mints a short-lived **signed identity assertion** (`omniagents.rpc.identity_assertion`: HMAC-SHA256, fixed version prefix so there is no attacker-influenced `alg`, 60 s lifetime with a 300 s verification cap, audience-bound, single-use via a `jti` replay cache, header-only) naming the principal it authenticated, per connection, for `/ws`, `/ws/realtime` and `/ws/terminal` alike. The upstream validates it with the new `proxy_assertion` auth provider and resolves the asserted principal, so `authorize_rpc` upstream sees distinct users and cross-user attempts are refused with `-32014` back through the proxy. Configure with `remote_agent.identity_secret_env` (+ optional `identity_audience`) on the proxy and `security.providers.auth: {type: proxy_assertion, signing_secret: ...}` upstream. The shared-token path is now **explicitly gated as single-tenant only**: a proxy whose own authenticator identifies distinct principals refuses to start with it configured, as does an unresolved/short (<32 char) signing secret or both schemes configured at once — there is no silent fallback.

### Changed (BREAKING)
- Tracing is off by default. `ProjectContext.tracing_defaults` is now `{provider: none, project: <slug>, name: <slug>}` and `setup_tracing(None)` disables tracing; set `tracing: {provider: studio}` in `project.yml` to record locally. An always-on recorder grew `~/.omniagents/traces` without bound (8 GB on one desktop). Evaluations still record locally unless the manifest declares a provider, since Studio's review screens read them. The `default` provider alias is gone.
- **A single shared `token:` (including `serve --token X`) no longer reports that it identifies distinct principals.** Every holder of one shared token authenticates as `user_id="token_user"`, so claiming otherwise let a proxy boot advertising per-user identity while minting the same subject for everyone — the exact vulnerability this release fixes, reachable through the migration path above. Only the multi-token `tokens:` map is per-user. Deployments using a single shared token behind a proxy must move to `tokens:` (or accept the documented single-tenant shared-identity mode).

  `AuthProvider` gained a third capability, `enforces_authorization`, so this change does **not** relax authorization: a shared-token deployment still runs with ownership and global-effect rules enforced (`disable_tool` and friends refused, unclassified methods default-denied). Only the genuinely unauthenticated `none` provider is permissive, exactly as before. `CompositeAuthProvider` aggregates the two capability claims as conjunctions and enforcement as a disjunction, and propagates a member's transient-capacity refusal so a composite at capacity answers a retryable 503/1013 rather than a terminal 4401.
- `TokenAuthProvider` now refuses a configuration that sets **both** `token:` and `tokens:`. The pair has no coherent reading — `token` maps every holder to one `token_user`, `tokens` maps each credential to its own user — and it previously failed open on the proxy branch, selecting a single shared upstream identity for genuinely distinct users. Configure exactly one; use `tokens:` for multi-user deployments.

- **A proxy (`remote_agent.ws_url`) that authenticates its own users no longer starts with a shared upstream token.** This is the fix above, and it is breaking on purpose: the previous configuration booted fine and silently presented every local user to the upstream as one identity. Affected shape: a `remote_agent:` config whose spec also sets `security.providers.auth` (including `omniagents serve --token X` against a proxy config).

  **Migration.** Set `remote_agent.identity_secret_env: <VAR>` on the proxy and configure the upstream with `security.providers.auth: {type: proxy_assertion, signing_secret_env: <VAR>}`, sharing one random ≥32-character secret. If the upstream *also* serves direct (non-proxied) clients, do not swap its provider — wrap both with the new `composite` provider: `{type: composite, accept: [{type: proxy_assertion, ...}, {type: oidc, ...}]}`. Deleting the proxy's own authentication also makes the error go away and is **not** a valid migration: it re-creates exactly the vulnerability this release fixes, so the startup error names the supported options instead.

  The symmetric case is refused too: an identity secret on a proxy that authenticates nobody would name every assertion `anonymous`, which upstream means one owner for all sessions.

- `AuthProvider` gained two declared capabilities, `identifies_principals` and `supports_connect_tickets` (both defaulting to `True`, the fail-closed answer). `ConnectionAuthenticator.identifies_principals` now reads the declared attribute instead of `isinstance`-testing the provider. Custom providers are unaffected unless they subclass `NoneAuthProvider` *and* resolve distinct principals — that shape (a gateway-header provider in front of Azure EasyAuth / oauth2-proxy) was previously read as single-user, which disabled ownership enforcement and let the serve proxy collapse every user onto one upstream identity; it must now set `identifies_principals = True`. That single flag is sufficient — `NoneAuthProvider.enforces_authorization` follows it, so declaring per-user identity re-enables ownership enforcement automatically rather than requiring a second flag an operator could miss (missing it would fail open: per-user identity propagated upstream while the local server ran with no ownership checks).
- The serve proxy relays the upstream's WebSocket close code instead of flattening it to 1000/1011, and maps a rejected upstream handshake to a terminal 4401. Proxied clients now see 4401/4403 as terminal, matching the direct-connection contract, instead of treating an authorization refusal as a retryable disconnect.
- `POST /auth/ws-ticket` is no longer registered when the configured provider declines connect tickets (`proxy_assertion`). Browsers never reach such an upstream, and the ticket would have moved a proxy-derived credential into a query string with a fresh TTL.

Completes the recap/compaction symmetry for offline session summarization (`omniagents.core.session.summarize`): products install a summarizer with `set_session_summarizer` (their session-summarizer agent + model resolution; the callable receives `(prompt, *, model, project, agent, session_id)`), and `DEFAULT_SESSION_SUMMARY_INSTRUCTIONS` is a ready-made summarizer system prompt (lifted from omni-code's session_summarizer agent and domain-neutralized). The envelope's content keys are a parameter of the flow (`envelope=` on `summarize_session`, `args.summary_envelope` on the CLI mount) with a neutral default (`DEFAULT_SESSION_ENVELOPE`), so products keep their domain-flavored keys.
- Model runtime/provider plumbing beside `ModelConfigStore` (`omniagents.core.models`), lifted from omni-code: `resolve_model_runtime` (ref → `(model_name, runtime)` with optional prefix normalization) and `resolve_service_model_runtime` (utility-run preference order: session active model → service spec model → raw session `model_config`), both taking an explicit `store=` or the process-wide registry installed via `set_model_store`; `normalize_model_name` (runtime-side counterpart of the store's ref parsing — strips non-`openai/`/`litellm/` provider prefixes, keeps LiteLLM ids whole); and `provider_from_runtime`, the runtime-dict → SDK model-provider adapter over `run_options.build_model_provider` that adds the credential policy the plain builder does not apply (litellm API-key env overrides, env-var credential fallback, "no credential against a real OpenAI/Azure endpoint → no provider", dummy key for local endpoints).
- Governed model config producer (`omniagents.core.models.governed`): `write_governed_config` / `load_governed_config` / `governed_config_path` own the `models.governed.json` artifact next to `models.json` — `_governed`/`_allow_user_models` markers, per-provider `_governed` stamping, merge-base vs replace semantics read back by the store's layered merge, 0600 permissions — parameterized by config dir. Products keep only the policy-key extraction that feeds it.
- `container_runtime()` / `container_runtime_available()` (`omniagents.core.sandbox.container_runtime`): docker/podman CLI selection honoring `OMNIAGENTS_CONTAINER_RUNTIME`, with an `env_vars` seam so products can put their own operator knob first (omni-code: `OMNI_CONTAINER_RUNTIME`). CLI-binary concept only — the docker sandbox backend keeps talking to the engine API via the docker SDK (`DOCKER_HOST` covers Podman's docker-compatible socket there).
- `resolve_prompt_file(candidates, fallback, max_bytes=...)` (`omniagents.core.utils.prompt_files`): user-overridable prompt-file resolution — first non-empty candidate (workspace file, then user-config file), size-capped and error-tolerant, else the builtin fallback text. Lifted from omni-code's loop-prompt resolution; pairs with the `set_loop_default_prompt_resolver` seam.
- `UserMcpFixtureStager` (`omniagents.core.eval.mcp_fixture`): per-scenario user-MCP fixture staging for eval environments — isolated `XDG_CONFIG_HOME` inside the scenario temp dir, fixture file/tree copies, generated `<product>/mcp.json`, and an `env_vars()` contribution for `get_env_vars()`. Lifted from omni-code's `WorkspaceEvalEnvironment` minus its cross-scenario lock, which the runner fix below makes unnecessary.
- The builtin `shell` / `shell_readonly` packs now steer discovery toward the shell over the filesystem discovery tools when piping/chaining (`| head`, `| xargs`) helps — restoring a nuance from omni-code's retired filesystem-pack override.
- The environment-backed eval runner (`run_scenario`) now applies environment-declared env vars (`get_env_vars()`) *before* loading the agent spec, not after. Spec loading reads the process env — notably `XDG_CONFIG_HOME` for `allow_user_mcp_servers` discovery — so environments staging per-scenario config previously had to mutate `os.environ` in `setup()` under a self-managed lock. With no awaits between application and spec load, each concurrent scenario's spec load reads its own values.
