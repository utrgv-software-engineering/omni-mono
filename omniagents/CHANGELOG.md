## [0.7.23] - 2026-07-22

### Added
- One-name convention over configuration: a product manifest now needs only `product: {name: acme-agent}` and every identity facet derives — `slug` (name with `-`→`_`), `prog` (name), `label` (name split on `-`/`_`, title-cased: `omni-code` → "Omni Code"), `config_dir` (slug), `windows_config_dir` (label without spaces: "OmniCode"), `env_prefix` (slug upper-cased), and `update.command_hint` ("`<prog> update`"). Explicit keys still win everywhere. The product identity IS the project identity: `load_project` resolves the manifest's `product:` section (deriving from the project directory name when absent) into `ProjectContext.product`, and everything that historically read the top-level `name:` now scopes by `product.slug` — spec `project_slug` (sessions/history registries), the user-MCP config dir, the config-dir overlay chain (`<product-config>/project.d/`), the Studio playground project name, and the eval loader's introspection `project_name`. Tracing derives too: `ProjectContext.tracing_defaults` is always `{provider: studio, project: <slug>, name: <slug>}` with a declared `tracing:` block deep-merged over it (the eval loader's `tracing_config` reuses it), and `setup_tracing`'s bare-run fallback project is the installed product slug. Entrypoints are deliberately NOT part of the convention: which agent runs must be declared (`agents.entrypoint` / `agents.voice_entrypoint`); only the historical single-agent auto-entrypoint remains, and resolving a multi-agent project with no declaration fails with an error naming the `agents.entrypoint` key. Paths gain the last conventional default: an undeclared model catalog resolves to a manifest-sibling `models.yml` when the file exists (mirroring the sandbox-profile sibling convention); an explicit `paths.model_catalog` still always resolves. The `omniagents new` scaffold now emits the minimal showcase manifest: a `product:` block with the name plus an explicit `agents: {entrypoint: ...}` declaration.
- Declarative eval environments (`omniagents.core.eval.environment_config`): the `evaluation.environment` block now declares the environment as data — a `type` naming a registered environment factory plus that factory's knobs — and the framework builds it; products keep no environment Python. The built-in `local_workspace` type composes the workspace-eval machinery end to end: every `LocalWorkspaceEnvironment` knob (`fixtures_dir`, `workspace_root`, `skills_subdir`, `keep_tempdir_env`, `tempdir_prefix`; relative paths resolve against `evaluations/`), a static `env:` map with `${workspace}` (per-scenario temp dir) / `${workspace_root}` (cache root) expansion and unknown-token passthrough, `container_routing:` composing `ContainerRoutingMixin` (`profile_resolver: product` → `resolve_product_profile`, or a dotted import path; `default_profile` for the bare `environment.image` shorthand; optional `profile`/`image` class-level fallbacks), and `mcp_fixture:` parameterizing per-scenario user-MCP staging (the `UserMcpFixtureStager` path lifted from omni-code's `WorkspaceEvalEnvironment`): `scenario_key` opts a scenario in, `<dbs_dir>/<name>.db` / `<name>.pages` stage into an isolated XDG_CONFIG_HOME as `db_dest`/`pages_dest`, and the generated mcp.json uses the declared `server_name`/`command`/`cli`/`args` — `cli` and `command` are `{env_var, default}` pairs preserving the env-var-overrides-declared-default resolution (a broken override fails loudly rather than falling back). Environments that genuinely aren't configuration register a factory via `register_environment_type` from project Python the pipeline already imports (`evaluations/measures.py`); this lets omni-code delete `environments/workspace_env.py` and `environments/devbox_env.py` outright and declare the same environment in `evaluation.yml`.

### Removed
- The framework no longer ships agent prompt text at runtime — batteries moved to the scaffold, products own every word their agents speak. Deleted: `DEFAULT_RECAP_INSTRUCTIONS` (`core/runtime/recap.py`), `DEFAULT_CHECKPOINT_SUMMARY_INSTRUCTIONS` (`core/runtime/compaction.py` — the checkpoint ENVELOPE text stays: it is orchestration framing the framework wraps around the summarizer's output, not an agent's system prompt), `DEFAULT_SESSION_SUMMARY_INSTRUCTIONS` (`core/session/summarize.py`, and its `omniagents.core.session` re-export), `DEFAULT_WORKER_INSTRUCTIONS` / `apply_default_worker_instructions` / `default_worker_instructions_path` / the packaged `worker_instructions.md` (`core/workers/instructions.py`, whole module) and the `WorkerManager` seam that applied it at spawn — a worker spec that declares no instructions now gets exactly what the YAML loader historically did: the generic "You are a helpful assistant." fallback plus its warning.
- Builtin instruction fragments are gone: `omniagents/builtin/instructions/` (`personality.md`, `proactiveness.md`, `agents_md_spec.md`, `task_execution.md`) is deleted, `instruction_search_paths` no longer appends a builtin tail, `_build_loader` no longer mounts the `builtin/` PrefixLoader prefix, and `builtin_instruction_fragments_dir()` is removed — missing-include errors list only project-side paths. The package-data glob for `instructions/*.md` and the `omniagents.core.workers` markdown glob are dropped. The same texts now ship as `omniagents new` scaffold output under the generated project's `agents/_shared/` (and the battery agents' `instructions.md`), owned by the product.
- The top-level `name:` key in project.yml is gone as a concept — the `product:` section (or, absent one, the project directory name) is the single identity source. No loader/runtime path reads it anymore: `_project_overlay_paths`, the user-MCP slug, `build_spec_from_project`'s `project_slug`, the Studio playground/api project name, the eval loader's `project_name`, and the CLI's studio-project manifest fallback all derive from the resolved product identity. A leftover `name:` key is inert. All framework examples, fixtures, and the project template moved to the `product:` form.
- The class-path eval-environment mechanism (`evaluation.environment: {class: ..., config: ...}` and `load_environment_class`) is gone; the declarative `environment:` form above is the only mechanism. A declared environment that fails to build is still reported as `environment_error` + warning in the eval result, with scenarios running environment-less. The `eval_with_environment` example now registers its demo factory from `evaluations/measures.py` and declares `type: booking_demo`.
- Product prompt-template files (`omniagents.core.project.prompts`): a product ships prompt wording as data — Markdown files in the directory `paths: {prompts: <dir>}` names (manifest-relative, default the `prompts/` sibling of project.yml) — instead of Python modules of f-strings. Conventional filenames bind each file to a framework seam: `goal_initial.md` (first user message of a `/goal` autopilot run) and `goal_tick.md` (periodic tick body), both rendered with the goal context (Jinja variables `goal`, `max_turns`) through the same environment as agent instructions (silent-undefined, output stripped — so moving a prompt from an f-string builder ending in `.strip()` to a file is byte-preserving); and `loop.md` (the default `/loop` body when `/loop` is invoked without text). Precedence at each seam: an explicitly installed builder/resolver (`set_goal_prompt_builders` / `set_loop_default_prompt_resolver`) always wins; else the product template file; else the framework's generic default. The `/loop` default is now a fully conventional chain in the framework — `<workspace>/.<prog>/loop.md` (the workspace override dir derives from the product's CLI prog, preserving omni-code's historical `.omni/`) → `<config-dir>/loop.md` → packaged `prompts/loop.md` → none — so omni-code's `goal_prompts.py` / `loop_prompts.py` and their `context.py` install calls are deleted; its prompts move verbatim into `omni_code/prompts/*.md` (byte-parity pinned product-side). Resolution is a light manifest read against the installed product identity (`product_info().manifest_path`) mirroring `resolve_project_agent_yaml`; `load_project` also resolves `paths.prompts` into `ProjectContext.paths["prompts"]`.
- Declarative slash → project-agent bindings (`omniagents.core.runtime.slash_agents`): `slash_commands:` in project.yml binds a slash command to a one-shot project agent run — `agent` (required key under `paths.agents`), `prompt` (kickoff message, default `begin`), `max_turns` (default 50), `normalize_model` (default true; false keeps the runtime's raw model id), `failure_message` (returned when the run raises), and an optional `attach_file` success protocol (`path`, `when_status`, `language`): when the agent's final line is one of `when_status` and the workspace file exists, the response becomes `<status>\n\n<path>:\n\n```<language>\n<body>\n``` ` — byte-compatible with the `/init` handler this lifts from omni-code. The generic runner resolves the configured default model via `resolve_model_runtime`, stamps the runtime's `model_settings`, anchors the run to the invoking shell's directory (`$PWD` → cwd), and executes multi-turn through `run_project_agent_once`; the final-line protocol lives in the bound agent's instructions (product content), the mechanics in the runner, the binding in data. The default slash registry (`omniagents.core.tools.slash_commands`) falls back to manifest bindings whenever no Python-registered handler exists for a name — a `register_slash_command` handler of the same name always wins — so omni-code's `init_command.py` and its `register_slash_command("init", ...)` wiring are deleted; `/init` is four lines of YAML.
- Conventional summarizers: the three summarizer seams now resolve by agent-naming convention, so products stop installing near-identical callables. With no explicitly-installed summarizer, `recap_summarizer()` / `compaction_summarizer()` / `session_summarizer()` fall back to running the project agent named by convention — `recapper`, `compactor`, `session_summarizer` under the installed product's manifest — one-shot via `run_project_agent_once`, always under the agent's own `instructions.md`: the prompt each summarizer speaks is product content (the framework ships no agent prompt text at runtime; `omniagents new` scaffolds the starter agents). Recap/compaction use the utility-run model preference order (`resolve_service_model_runtime`: session active model → service spec model → session model_config); the session summarizer (whose JSON schema must agree with the product's summary envelope) runs on `resolve_model_runtime(--model or default)`, failing with actionable `No model configured. Run: <prog> model setup` errors derived from the product identity. Mechanism: lazy fallback inside the seam getters, so an explicit `set_*_summarizer` install always wins and installing `None` restores the convention; a project without the conventional agent behaves exactly as before (clear not-installed errors). Shared factory: `omniagents.core.runtime.conventional_service_summarizer(agent_key)` — no instructions parameter, there is no injection path. The ephemeral harness also gains `ephemeral_workspace_root(session)` (lifted from omni-code): `run_agent_once`'s workspace-root fallback is now session context → published sandbox manifest root → process cwd, so conventional summarizer runs anchor correctly under container backends.
- `omniagents new` scaffolds the battery agents and shared instruction fragments as starter content the product owns: `agents/recapper/`, `agents/compactor/`, `agents/session_summarizer/` (neutral-envelope JSON schema prompt), and `agents/worker/` (the generic worker protocol — stay-focused, parallel tool calls, absolute paths, private task-list scoping, when-stuck protocol, structured output format — flattened to plain markdown; no Jinja hooks the scaffolded project does not feed), each `agent.yml + instructions.md`; plus `agents/_shared/{personality,proactiveness,agents_md_spec,task_execution}.md` (task_execution flattened with the descriptor "agent"), included by the scaffolded entrypoint agent's instructions. `delete_agent` prefers a non-battery agent when reassigning the manifest entrypoint.
- Manifest-declared session summary envelope: `sessions.summary_envelope` in project.yml maps content keys to per-call defaults for `sessions summarize` (`omniagents.core.session.summarize.manifest_session_envelope`). The framework sessions CLI reads it whenever no `args.summary_envelope` was pinned (an explicit namespace envelope still wins); absent or malformed declarations fall back to `DEFAULT_SESSION_ENVELOPE`. Together with the conventional summarizer this deletes the last product-side sessions glue: omni-code's `sessions` COMMANDS override, its summarizer callables, and its `utility_runs.py` are gone — and the codex conditional import that module carried is proven redundant (openai-oauth builder registration happens on `import omniagents`; verified by a fresh-interpreter resolution smoke with no product import).
- Reserved `serve` subcommand (`omniagents.product_serve.serve_main`, mounted by `omniagents.product_cli` like model/auth/update/sessions): any product with a `product:` block gets a launcher-compatible `<prog> serve` from convention — the exact spawn argv the desktop launcher builds (`--output json`, repeatable `--source`/`--credential` JSON descriptors, `--project`, `--snapshot-dir`, `--session-id`, `--container-id`, `--profile`, `--workspace`; no port flag — serve picks and reports it), profile resolution through the new conventional product chain, entrypoint-agent spec load via `load_project` off the installed product manifest (or `--agent-project`), the serve harness bring-up (sandbox or `host` target), FastAPI/uvicorn with sandbox-aware workspace-root clamping, terminal-manager install per target, idle auto-recap, the single-line JSON readiness payload (field-for-field the launcher's `SandboxJsonPayload`, factored as `build_readiness_payload` so the contract gate pins it), `SwitchContext` publication + `perform_switch` executor install, fast signal shutdown (SIGTERM/SIGINT/SIGHUP skip uvicorn's drain, bounded run-quiesce, teardown-finally with snapshot persist), and structured `{"error": ...}` stderr lines + nonzero exit for launch failures. Codex (openai-oauth) provider registration is conventional too: registered exactly when the product's declared model catalog contains an `openai-oauth` provider. Products can still override `serve` via `cli.extensions` `COMMANDS`, but the default is launcher-complete — omni-code's 677-line `serve_cli.py` dissolves.
- Reserved `sandbox-host` subcommand (`omniagents.product_serve.sandbox_host_main`): the laptop half of computer-as-sandbox — bind a loopback WebSocket, hand each connection to `host_bridge.serve_host_connection`, print the `{"exec_port": N, "host": ...}` first-stdout-line handshake (`exec_port_payload`). Absorbs omni-code's `sandbox_host_cli.py`.
- Reserved `describe` subcommand (`omniagents.product_cli.run_product_describe_command`): `<prog> describe --json` prints one JSON object — `name`, `prog`, `label`, `slug`, `version` (product distribution version via importlib.metadata, framework version fallback), `config_dir` (resolved absolute), `env_prefix`, `update` (`{index_url, command_hint}` or null), and `serve_protocol` — so launchers can introspect an installation and verify contract compatibility before spawning.
- The serve wire contract is now a versioned framework document: `docs/serve-protocol.md` (protocol version 1, `omniagents.product_serve.SERVE_PROTOCOL_VERSION`) specifies the spawn argv, source/credential descriptor JSON, readiness-payload shape (including optional-field tolerance and the `default=str` serialization guarantee), the launch-failure error protocol, the post-ready surface (ui_url polling, `/ws`, `sandbox.*`/`session.ensure`/`terminal.create` server calls), the sandbox-host handshake, and `describe`. Contract-gated by `tests/unit/test_product_serve.py`: the parser accepts argv built literally from the launcher's spawn code, the payload dict byte-matches the documented shape (keys, order, values), and the exec_port line format is pinned.
- Conventional product profile default (`omniagents.core.sandbox.profiles`): `product_default_profile_path()` resolves a product's packaged base profile from its manifest — `paths: {sandbox_profile: <file>}` when declared (manifest-relative, mirroring `paths.model_catalog`), else the conventional `sandbox_profile_default.yml` sibling of project.yml (exactly where omni-code ships it) — and `resolve_product_profile(...)` is `resolve_profile` with that default layer bound, the resolver the reserved `serve` uses at boot and hands to `SwitchContext.profile_resolver` so `sandbox.switch` resolves identically mid-session. Products without a packaged default degrade to the user/project layers only.
- Entry-point product discovery (`omniagents.core.product`): installed product distributions declare an `omniagents.products` entry point whose value is a *module reference* — the importable package shipping the product's `project.yml` as a top-level resource (`omni-code = "omni_code"`). A module reference (not a file path, not a loaded attribute) is robust across editable and wheel installs: it resolves through the import system to wherever the package lives (via `importlib.resources.files`, `__file__`-sibling fallback), and needs no code execution beyond importing the product package, whose `__init__` is now expected to be side-effect free. `product_info()` resolution becomes: explicitly-set (`bootstrap_product`/`set_product_info`) → `load_project`'s implicit install → entry-point-discovered (lazy, cached; deterministic lexicographic pick + stderr warning when multiple distributions declare one; broken declarations warn and degrade) → the framework's `omniagents` default — so identity (config dir, slug, prog) resolves correctly even on bare module imports with no prior bootstrap. `discover_product_manifest()` exposes the discovered packaged manifest; `reset_product_info()` clears the discovery cache; `OMNIAGENTS_PRODUCT_DISCOVERY=0` disables discovery (the framework's own test suite pins this so dev-environment products don't leak in).
- Generic console-script entries in `omniagents.product_cli`: `main(argv=None)` — the direct `[project.scripts]` target for a product CLI (`omni = "omniagents.product_cli:main"`), resolving the packaged manifest via entry-point discovery and delegating to `product_main` (exit 2 with a clear stderr message when no distribution declares a product) — and `setup_main()` — the standalone model-wizard shortcut for `omni-setup`-style scripts (bootstraps the discovered product, then `model setup` on the installed store, generic product-config-dir store fallback). omni-code's `cli.py` dispatcher module is deleted outright; its `pyproject` names the framework targets.
- Models bootstrap is a fallthrough convention of the product CLI host: for products with an installed process-wide model store (built at `bootstrap_product` from the manifest's declared `paths.model_catalog`), the fallthrough agent run now loads the user model config, applies platform model governance (best-effort, authenticated only), exports `MODEL_NAME` from the resolved runtime, and — when no models are configured — runs the interactive setup wizard, exactly the gating omni-code's `models_preflight` had: agent-run invocations only (never ahead of subcommand dispatch), wizard replaced by a single `{"error": "No model credentials configured"}` JSON line + exit 1 in embedded mode. Products without a catalog (no installed store) skip it entirely; omni-code's preflight is deleted.
- Embedded (non-serve) launch is framework launcher contract: `--embedded` on a fallthrough invocation is intercepted by `product_main` — flag stripped, `OMNI_WEB_AUTO_OPEN=false` and `<ENV_PREFIX>_UPDATE_CHECK=0` exported (the launcher owns the window and update UX; the notice dies through the standard updater env gate), and `--mode web` without an explicit `--output` gets `--output json` appended. Ignored on subcommand dispatch, matching omni-code's `dispatches_to_command` self-gating. Documented in `docs/serve-protocol.md` (`<prog> --embedded`, a sibling section of `serve`); omni-code's `embedded_preflight` is deleted and its `cli_extensions.PREFLIGHT` now carries exactly the governance sandbox re-exec.


## [0.7.22] - 2026-07-18

### Added
- Declarative model catalog (`omniagents.core.models.catalog`): a product's shipped provider/model catalog is data, so it now lives in a YAML file referenced from the manifest — `paths: {model_catalog: models.yml}` (a sibling-file reference, not an inline block: `paths.*` entries are already manifest-relative shipped assets, catalogs are long, and the file ships in the wheel exactly like project.yml). Schema: `providers` (the exact provider/model shape `ModelConfigStore` consumes, `${VAR}` expanded by the store at resolve time), `default_model` (fallback default ref), `default_provider` (implied by unprefixed refs; default `openai`), with unknown-key typo protection like `product:`. The framework builds + installs the store from the declared catalog with *conventional hooks*: config dir late-bound from the installed product identity, governed config from the standard `models.governed.json` location gated on management-plane auth (a stale governed cache never applies signed-out) and re-applied once from the platform policy when credentials exist but the cache is missing, codex OAuth live discovery + sign-in state wired only when the catalog contains an `openai-oauth` provider, and conventional platform credential vending. Install timing: `bootstrap_product` (so pre-project CLI paths — the model wizard, `<prog> model`/`provider` — see the catalog) and `load_project` (implicit), through a new default-store seam in `omniagents.core.models` mirroring the product-identity precedence — an explicit `set_model_store` always wins and is never clobbered; among conventional installs the most recent wins, and installing the same catalog twice re-installs the same store instance (per-catalog memoization). `reset_model_store()` clears everything for tests. Lifted to power the conventional hooks: the policy-to-governed-file application moves into `omniagents.core.models.governed` (`get_cached_platform_policy` / `fetch_and_cache_platform_policy` / `apply_platform_model_governance` — the policy's `model_providers` / `project.allow_user_models` / `project.default_model` keys are a platform client contract, so no product extraction code remains), and process-cached credential vending into `omniagents.core.providers.platform.credentials.fetch_provider_credential` (local sessions bootstrapped for the installed product slug). omni-code's `default_models.py` and `models.py` are deleted outright — the catalog is `omni_code/models.yml` and every call site reads the installed store via `model_store()`.
- Governance re-exec helper (`omniagents.core.sandbox.process_relaunch`): the domain-generic mechanics of "relaunch the current Python process inside `omni-sandbox exec` with the right binds", lifted from omni-code's governance so a governed product's `governance.py` shrinks to pure policy translation. Surface: `is_sandboxed()` (authoritative Linux user-namespace detection via `/proc/self/uid_map`, `OMNI_SANDBOXED` env fallback elsewhere — enforcement never nests), `find_sandbox_binary(candidates)` (discovery order `OMNI_SANDBOX_BIN` env var → caller-supplied packaged-assets/sibling-checkout candidates → `PATH`; returns `None` so the caller owns the missing-binary refusal whose text names product install channels), `editable_source_dirs(venv_dir)` (source dirs of `pip install -e` installs — legacy `.pth` and modern `__editable___*_finder.py` MAPPING layouts — which must be bind-mounted for imports to resolve inside the sandbox), and the typed relaunch core: `SandboxRelaunchRequest` (workspace, `network: none|unrestricted`, host-allowlist, pids/disk limits, ignored relaxations, protected subpaths, ordered `SandboxBind` mounts, backend label, argv override) + `build_relaunch_argv` / `relaunch_in_sandbox` (`os.execvp`, re-execing the realpath of the entry script with its venv and editable sources auto-bound). Fail-closed semantics are byte-compatible with omni-code's governance, whose tests pin the message shapes: host-filtered network allowlist → refusal (the process sandbox cannot do per-host egress filtering), disk quota → refusal, security-profile relaxations → stderr note then ignored (running stricter is safe), `pids_limit` → `--pids-limit` passthrough. `omni_sandbox_exec_argv` is now the one canonical `omni-sandbox exec` argv builder, shared with the `process` sandbox backend (`process_extended._confined_exec_command` delegates to it) so the wire format cannot drift; canonical flag order is workspace → net → pids → protect → binds (the relaunch path's byte-parity-pinned order — the process backend's binds moved after `--net`/`--protect`, an order-only change the CLI parses identically).
- `process` sandbox backend (`omniagents.core.sandbox.process_extended`): a unix_local-shaped client whose every exec — batched execs, PTY shells, and the exec-based file ops — is wrapped in the standalone `omni-sandbox` binary (`omni-sandbox exec --workspace <manifest root> [--ro-bind]... [--rw-bind]... [--net] [--protect]... -- <command>`), giving platform-native process isolation (Linux bwrap+seccomp, macOS seatbelt, Windows AppContainer) without a container engine. Profile schema under `sandbox.client`: `type: process`, optional `binary` (explicit path), `ro_binds`/`rw_binds` (extra mounts), `network: none|unrestricted` (`unrestricted` → `--net`; default blocked), `protected_subpaths` (one `--protect` per entry; omitted → the binary's `.git`/`.env`/`.codex` defaults). Binary discovery at construction time, fail closed: explicit `binary` key → `OMNI_SANDBOX_BIN` env var → `PATH`, with a missing binary raising immediately and naming the install options. Network is all-or-nothing by design: a profile demanding a `network_allow` host allowlist fails closed at construction (mirroring omni-code's governance message shape) because the process sandbox cannot enforce host-level egress filtering — use a container backend for allowlisting. The client mixes in `LifecycleSessionClientMixin` like the other extended clients, so pause/unpause are cleanly reported unsupported by the lifecycle proxies; `ExtendedUnixLocalSandboxClient` gains a `_make_inner_session` seam the process client overrides to stamp the wrapper config on its sessions.
- Project-aware ephemeral runs: `omniagents.core.runtime.run_project_agent_once(agent_key, prompt, ...)` resolves `agents/<agent_key>/agent.yml` through a project manifest (explicit `project_path=`, else the installed product's manifest) and delegates to `run_agent_once`, absorbing the spec-level overrides every product utility-runner re-implemented — `model_settings` stamped on the loaded spec, `instructions` replacing the spec's system prompt for prompts whose source of truth lives in code, and an optional `runtime=` dict turned into an SDK provider via `provider_from_runtime` when no explicit `model_provider`/`env_overrides` are passed (products with provider policy of their own keep resolving those themselves). Resolution is a light manifest read (`paths.agents`, default `agents`; first hit wins across multiple dirs), exposed as `resolve_project_agent_yaml`. To make the default manifest discoverable, `ProductInfo` gains a `manifest_path` field stamped by `load_product_info`/`bootstrap_product` and by `load_project`'s implicit identity install; hand-built infos keep `None`. omni-code's `run_utility_agent` shrinks to a thin delegate.
- Builtin instruction fragments: the framework now ships generic agent-harness instruction fragments as data files under `omniagents/builtin/instructions/` (`personality.md`, `proactiveness.md`, `agents_md_spec.md`, `task_execution.md` — the last parameterized by `task_execution_agent_descriptor`, defaulting to "agent"), lifted from omni-code's `agents/_shared/`. `instruction_search_paths` appends the builtin directory *last*, so a bare `{% include "proactiveness.md" %}` falls through to the builtin only when no project fragment of that name exists — project fragments shadow builtins by name, mirroring builtin-capability/agent precedence. The include loader additionally mounts the builtin directory under the explicit `builtin/` prefix (`{% include "builtin/task_execution.md" %}`), which bypasses shadowing — the escape hatch that lets a project fragment extend its builtin namesake (include + delta) without recursing into itself. `builtin_instruction_fragments_dir()` exposes the location; `InstructionIncludeNotFoundError` now lists the builtin directory among the searched paths.
- Process-global serve-session state (`omniagents.core.runtime.serve_state`), lifted wholesale from omni-code's `agent_workspace_state`: the serve host publishes the running session's wiring — `manifest_root`, the parsed launcher `--source` descriptors (raw dicts preserved for UI callers, plus a typed `SourceDescriptor` view via `get_source_descriptors()` with `kind`/`mount_name`/`path`/`repo_url`/`ref`, `is_local`/`is_git`/`local_path()` helpers, and `from_dict`/`to_dict` round-trip of the wire protocol), the resolved `ProjectContext`, the sandbox-attached orchestrator `AgentSpec`, the live `SandboxSession`, the discard-snapshot-on-exit flag, and the sandbox-profile `SwitchContext` — and every other consumer (server functions, worker spec loaders, skill-root resolution, context factories) reads it without weaving references through call sites. All slots default to absent so non-serve entry points behave standalone; `reset()` restores that for tests.
- The `workspace_info` provider seams (`set_workspace_sources_provider` / `set_manifest_root_provider` / `set_sandbox_session_provider`) now DEFAULT to reading the published serve-session state — an explicitly-installed provider still wins. A product whose serve host publishes into `serve_state` no longer installs any of the three providers.
- Skill-root resolution is now derived, not product-installed: without a `set_skill_roots_provider` install, `skill_roots(workspace_root)` resolves `<workspace>/.{product slug}/skills`, then each published workspace source's `skills/` directory (`source_skill_roots` — mount-name resolution against the serve session's manifest root, host-path fallback when no sandbox session is live, order-preserving dedupe), then `<product config dir>/skills` — so a product with a `product:` section in project.yml gets its conventional layout (omni-code: `.omni_code/skills` + `~/.config/omni_code/skills`) with no code. The previous default (`.omniagents/skills` only, empty without a workspace root) is subsumed: the framework identity derives the same dot-dir, and the invocation directory (`$PWD`) is the fallback base. `default_skill_roots`, `source_skill_roots`, and `dedupe_skill_roots` are exported from `omniagents.core.skills`.
- Serve-session harness (`omniagents.core.runtime.serve_harness`), lifted from omni-code's `serve_cli.py`: the generic core of "serve an agent against a profile-resolved sandbox session". `bring_up_session` builds the sandbox client/manifest from a `ResolvedProfile` + `--source` descriptors (per-source seed entries, `run_as` user pre-declaration), creates-or-resumes the session (3-tier docker resume: `reused` warm reattach / `rehydrated` from the snapshot tar / `fresh`, reported as a tier tag), scrubs unsafe symlinks from the snapshot tar before hydrate (`_scrub_session_snapshot`), applies the profile's idle-pause threshold, configures boot-time git/CLI credentials (`gh` / `az devops`, token via env-var name only), runs profile init commands as root, and starts services reuse-aware (adopts an instance already holding its port on a warm container) with exposed-port URL resolution. `perform_switch` is the full in-place profile-switch orchestration (lock, run-quiesce, workspace carry off noop-snapshot backends, teardown, bring-up, spec/terminal re-wire, `ui.sandbox.*` broadcasts, rollback-to-previous on failure) — install it via the existing `sandbox_lifecycle.set_switch_executor` seam. `teardown_session` stops PTYs, defensively unpauses, persists (or discards) the workspace snapshot via `session.stop()`, and closes; `None`-safe and swallow-all so shutdown never wedges. `bring_up_host_target` covers the no-sandbox `host` execution target (process-default `HostWorkspace` with profile-gated `confine`). The harness publishes the serve-state it derives itself (manifest root, sources, live session, orchestrator spec on switch/rollback); products publish only what it cannot know (project context, boot-time orchestrator spec, the `SwitchContext`). Product knobs default to the omni-code values they were lifted with: `NOOP_SNAPSHOT_CLIENT_TYPES` (`unix_local`/`host_bridge` skip lifecycle snapshots), `DEFAULT_SERVICE_URL_SUFFIXES` (a `vnc` service gets the noVNC client page), and the new `SwitchContext.profile_resolver` field — the product's layered profile resolver, used by switch/rollback so product profile layers apply mid-session too (framework resolver is the fallback). omni-code's `serve_cli.py` shrinks to product wiring (CLI surface, spec loading, FastAPI app, readiness payload) over the harness.
- Serve-state-derived worker defaults (`omniagents.core.workers.serve_defaults`), lifted from omni-code's `workers_runtime.py`: `install_project_worker_defaults(model_resolver=None, agent_key="worker", project_slug=None, default_isolation="none")` is the one call a product makes to wire the whole worker subsystem, with every input derived from framework state. It registers `MultiSourceWorktreeIsolation` over the new `serve_worker_sources` provider as the `worktree` strategy — mapping the serve session's published `--source` descriptors to `WorkerSource` entries (git worktree for `local-git`/`git-remote`, plain copy for `local`, other kinds skipped; host path from the published `path`, else the mount under the manifest root; degrades to single-repo worktree behavior when no sources are published) — and installs a `make_project_worker_spec_loader` bound to `default_worker_project_context` (the published `ProjectContext`, with a cached `load_project` of the installed product's `manifest_path` as the non-serve fallback), the published orchestrator spec (sandbox attachment forwarding), the installed product's slug, and `default_worker_model_resolver` (the process-wide model store installed via `set_model_store`; `None` when no store is installed, leaving the spec as built). `model_resolver=` remains the one product hook for products with their own resolution policy. Idempotent; omni-code's `omni_code/workers_runtime.py` collapses to this single call.


## [0.7.21] - 2026-07-18

### Added
- Product CLI host (`omniagents.product_cli`), driven by project.yml: `product_main(project_path, argv=None) -> int` collapses a product's hand-rolled CLI dispatcher to a ~5-line console script — if the base command is `omni`, the update command is `omni update`, all from configuration. It bootstraps the product identity first (`bootstrap_product`), then mounts the reserved subcommands from convention: `model`/`provider` (framework model CLI on the installed process-wide model store, with a generic product-config-dir store as fallback), `auth` (platform login/logout/status + the `auth codex` passthrough), `update` (mounted ONLY when the manifest declares a `product.update:` block; `UpdaterConfig.from_product`), and `sessions` (framework sessions CLI pinned to the product slug as project and the manifest's `agents.entrypoint` as default agent — exported as `run_product_sessions_command` so product overrides can delegate). Everything else falls through to `omniagents run --project <manifest> --mode <cli.default_mode>` (default `ink`) with args passed through, a leading `--` forcing prompt mode even for reserved words, and the update notice printed on the fallthrough path only. Product-specific behavior plugs in via a manifest-declared extension module — `cli: {default_mode: ..., extensions: my_product.cli_extensions}` — which may define `PREFLIGHT: list[Callable[[list[str]], list[str] | None]]` (argv hooks run in order before any dispatch; may veto/exec or rewrite argv — governance sandbox re-exec, first-run wizards, embedded-mode interception) and `COMMANDS: dict[str, Callable[[list[str]], int | None]]` (extra subcommands or overrides of reserved ones). Dispatch precedence: PREFLIGHT → COMMANDS (product) → reserved (framework) → fallthrough run. `dispatches_to_command(argv, extra_commands=...)` is the public gate preflights use to run only on agent-run invocations; `load_product_cli_config` is the light `cli:` parse (unknown-key typo protection, like `product:`).
